### 0.2 计分规格（v3.0 目标，vanilla 1.0.1o，等级 1）

**一句话规格（基础 Chips×Mult）**：High Card 5×1 / Pair 10×2 / Two Pair 20×2 / Three of a Kind 30×3 / Straight 30×4 / Flush 35×4 / Full House 40×4 / Four of a Kind 60×7 / Straight Flush 100×8。

| 牌型 | 基础 Chips | 基础 Mult | 计分牌张数（只有参与牌型的牌计分） |
|---|---:|---:|---:|
| High Card 高牌 | 5 | 1 | 1（只计最高的一张） |
| Pair 对子 | 10 | 2 | 2 |
| Two Pair 两对 | 20 | 2 | 4 |
| Three of a Kind 三条 | 30 | 3 | 3 |
| Straight 顺子 | 30 | 4 | 5 |
| Flush 同花 | 35 | 4 | 5 |
| Full House 葫芦 | 40 | 4 | 5 |
| Four of a Kind 四条 | 60 | 7 | 4 |
| Straight Flush 同花顺 | 100 | 8 | 5 |

```
chips = 牌型基础 Chips + Σ(计分牌的牌面值: A=11, J/Q/K=10, 其余=面值) + Σ(joker add_chips)
mult  = 牌型基础 Mult，然后按【槽位从左到右】逐张应用 joker：+Mult 加算 / ×Mult 乘算
final = floor(chips × mult)      # 只在末尾 floor 一次，中间不取整
```

- **牌面值**：A=11、J/Q/K=10、其余按面值；顺子判定时 A 可作 1（A-2-3-4-5）或高点（10-J-Q-K-A），**计分时仍按 11**。
- **计分牌筛选**：与 W2 的“打出的每张牌都计点数码”不同，v3.0 只计参与牌型的牌（高牌 1 / 对子 2 / 两对 4 / 三条 3 / 顺子·同花·葫芦·同花顺 5 / 四条 4）。
- **等级**：固定等级 1，不实现 Planet 牌与手牌升级（excluded）。
- 与 W2 的差异属**改造项**，不是“实现偏差”；W2 的自定义倍率表（SF 12 / 4K 10 / FH 8 / FL 6 / ST 5 / 3K 4 / 2P 3 / P 2 / HC 1）仅作 L0 历史。

#### 0.8.2 为什么对拍没做（以及现在能声称什么）

- **阻塞原因**：本构建环境没有可访问的真实 Balatro 会话（**v2.2 当时口径**：D2 决定不接 Mod 链；该决策已被 v3.0 反转为接入 balatrobot），EFHIII 算分器网页也未实际取样。因此 §8 的 20 例人工记录与 5 例抽检**没有任何一行是实测数据**，全部保持 `PENDING`。
- **可以声称**：引擎在**自定义子集内**自洽、可复现（25/25 测试、同 seed 整局一致、`verify` 10/10 与独立暴力枚举一致、3 盲注能跑通）。
- **不能声称**：与原版分数一致、与原版牌型倍率一致、与原版 Joker 语义一致、同种子同局面。`docs/engine-fidelity.md` 的 6 条已知阻塞项（缺 hand-base Chips、倍率表不同、无计分牌筛选、夹具非原版、`7♥7♦→68` 冲突、`before` 语义）仍未解决。
- **补救路径（v3.0 更新）**：**旧 20 例人工 + 5 例抽检已降为辅助证据，不再作为主门槛**；主路径是 **A0–A4 对齐契约 + 真游戏捕获 / `save`–`load` 反事实回放**（§0.6，证据填 `docs/engine-fidelity.md` **A 表（真游戏捕获）+ B 表（`save`/`load` 反事实回放）**；第三方抽检见附录 D）。真游戏不可达时按 07 §6.5 降级为 `CAPTURE_REPLAY_ONLY` 并如实声明；场景 header 的 `fidelity_status` 仍写 `NOT_VERIFIED`，直到 A2/A3 签核。

#### 0.8.3 本次实现引入的、与原计划不同但**有意为之**的三点

1. **joker 用合成夹具而非"规范里的 8 个 joker"**：v2.1 规范只给了 8 个通用效果类型，没有具名与数值；实现把数值写成工程默认值并明确标注"不是原版数值"，避免伪造映射。
2. **牌型倍率表是自定义的**（同花顺 12 / 四条 10 / … / 高牌 1）：与文档 §3 表一致，但不是原版 level-1 倍率；这是规范给定值，不是实现偏差。
3. **`before` / `individual` 只作自定义标签**：用于分派键与 trace 记录，不表示实现了 SMODS 调度器。

### 1.1 规则语义对齐（v2.1 新增）

自建子集最容易犯的错不是"漏了规则"，而是"顺序和真游戏不一样"。因此 v2.1 增加一条硬约束：

- **effect 组合器必须按 `cardarea × phase` 分派**，而不是自创一套"先加后乘"的线性流程。语义参照：`docs.smods.dev` 的 Calculate Functions（`context.cardarea` = `G.play` / `G.hand` / `G.jokers`，阶段 = `before` / `individual` / `repetition` / `global`）与 `DivvyCr/Balatro-Simulation` 的纯函数分派实现。
- **8 个 joker 逐个建"语义卡"**：在 `docs/joker-semantics.md` 里为每个 joker 记录"触发区域 / 阶段 / 作用对象 / 修改量 / 是否受顺序影响 / 依据来源"。这张表是 W2 的实现清单，也是与社区语义对齐的证据。**v3.0 更新**：语义卡对象改为 8 个 vanilla 具名 Joker（§0.3），`before`/`individual` 仍只是**自定义标签**、不声称等价 SMODS `context.before`。
- **随机性用三态表达**：本子集的 8 个 joker 均为确定性效果，无需概率；但**弃牌 EV（O2）**的采样必须输出 `{mean, min, max}`，避免把单点估计当精确值。

## 2. 数据模型

> v3.0 只改**取值**不改**结构**：`Joker.jid` 从合成夹具（`jc_*`/`jm_*`/`jx_*`）换成 8 个 vanilla 具名 Joker 的 id（§0.3）；`jokers` 上限 3 → **5**（§0.4）。字段类型与序列化契约不变（A1 映射仍以本结构为目标）。`rng_state` 实际类型是 **JSON 字符串**（完整 `getstate()`），见 §0.8.1 的偏差记录。

```python
# bench/model.py
@dataclass(frozen=True, slots=True)
class Card:
    suit: int   # 0♠ 1♥ 2♦ 3♣
    rank: int   # 1(A) .. 13(K)

@dataclass(frozen=True, slots=True)
class Joker:
    jid: str        # "jc_flat_chips" / "jm_add_mult" / "jx_mul_mult"
    kind: str       # "add_chips" | "add_mult" | "mul_mult"
    value: int      # chips 增量 / mult 增量 / mult 倍率×100（避免浮点）

@dataclass
class GameState:
    blind_idx: int          # 0..2
    target: int
    total_score: int
    hand: list[Card]
    deck: list[Card]        # 剩余牌堆，顺序固定（决定补牌）
    jokers: list[Joker]     # ≤3
    hands_left: int
    discards_left: int
    phase: str              # "play" | "shop" | "done"
    rng_state: int          # random.Random.getstate() 序列化，保证可复现
    seed: int
```

**可复现的硬要求**：`rng_state` 必须能完整往返（`getstate`/`setstate`），否则"同 seed 复现"是假的。

## 3. 计分规则（W2 已实现的自定义公式 = L0 历史；v3.0 目标见 §0.2）

> 下面的公式与倍率表是 **W2 自定义子集**，与原版不一致（**无牌型基础 Chips**、倍率表不同、打出的每张牌都计点数码）。v3.0 必须改为 §0.2 的 vanilla 计分：牌型基础 Chips×Mult + 计分牌筛选 + 末尾 floor 一次。在该改造完成前，本节只能用于解释 L0 行为。

```
chips = Σ(牌面点数: A=11, J/Q/K=10, 其它=面值) + Σ(joker.add_chips)
mult  = 牌型倍率 + Σ(joker.add_mult)
mult  = mult × Π(joker.mul_mult)          # 按槽位从左到右，整数运算
final = floor(chips × mult)
```

| 牌型 | 判定（优先级从高到低） | mult |
|---|---|---|
| 同花顺 | 同花且 5 张连续 | 12 |
| 四条 | 4 张同点 | 10 |
| 葫芦 | 3+2 | 8 |
| 同花 | 5 张同花 | 6 |
| 顺子 | 5 张连续（A 可当 1 或 14） | 5 |
| 三条 | 3 张同点 | 4 |
| 两对 | 2+2 | 3 |
| 对子 | 2 张同点 | 2 |
| 高牌 | 其它 | 1 |

#### 效果分派顺序（v2.1 新增，对齐社区语义）

计分不是"把所有加成加起来"，而是**按区域与阶段依次触发**。本子集按如下顺序实现（v1 规则集）：

| 阶段 | 触发对象 | 本子集的效果 |
|---|---|---|
| `G.hand` / `before` | 手牌上的加成 | 无（本子集无手牌增强） |
| `G.play` / `individual` | 打出的每张牌 | 牌面 chips（A=11，J/Q/K=10，其余面值） |
| `G.play` / `repetition` | 打出的牌重复触发 | 无 |
| `G.jokers` / `before` | joker 的加算 | 3 个 `+chips`、3 个 `+mult`，按槽位从左到右 |
| `G.jokers` / `individual` | joker 的乘算 | 2 个 `×mult`，按槽位从左到右 |
| 最终结算 | — | `floor(chips × mult)`，中间不取整 |

> 为什么写这张表：`+mult` 与 `×mult` 的**相对顺序**会改变结果，而"按哪个阶段触发"是社区语义里最容易被忽略、也最容易造成对拍系统性偏差的部分。实现时若与 `docs.smods.dev` 的描述冲突，以文档为准并在 `docs/joker-semantics.md` 记差异。

**四个最容易错的地方**（对拍时要专门覆盖）：
1. **优先级顺序**：先判同花顺再判同花，否则同花顺被吞。
2. **A 的点数**：顺子里 A 可作 1（A-2-3-4-5）或 14（10-J-Q-K-A）；计分时按 11。
3. **joker 触发顺序**：`+mult` 与 `×mult` 前后顺序影响结果，固定"槽位从左到右"。
4. **取整时机**：先算完 chips/mult 再 `floor`，中间不取整。

## 5. 状态转移

```
play(cards):
  final = score(cards, jokers)
  total_score += final
  hands_left -= 1
  hand = hand - cards + draw(len(cards))        # 从 deck 顺序补牌
  if total_score >= target: phase = "shop"（最后一档则 "done"）
  elif hands_left == 0: phase = "done"（失败）

discard(cards):
  discards_left -= 1
  hand = hand - cards + draw(len(cards))

choose_joker(idx):
  jokers.append(shop_options[idx]) ; phase = "play"（进入下一档）
  target = NEXT_TARGET[blind_idx]
```

**每次转移都必须**：写入 `episode.jsonl`（`state_before` / `action` / `score_delta` / `state_after` 摘要），供后续归因与重放。

## 6. Oracle 设计（分层，必须标注精确性）

| 层 | 定义 | 实现 | 精确性 | 用途 |
|---|---|---|---|---|
| **O1 Local Oracle（play）** | 当前局面所有 `play` 动作中即时分最高者 | 全枚举 218 → 取 max | **exact** | 主指标 regret 的分母 |
| **O2 弃牌 EV（discard）** | 每个 `discard` 动作执行后，下一手 Local Oracle 分的期望 | 对剩余牌堆做 K=50 次固定种子抽样补牌，输出 `{mean, min, max}` 三态 | **approx**（MC 误差 + 区间） | 评估弃牌质量，只作排序参考 |
| **O3 Episode 参照** | 全程贪心（每步选 O1 最优）得到的累计分 | 模拟执行 | **approx**（贪心上界，非全局最优） | 长程参照，不进主指标 |

**严禁宣称**：
- ❌ "局部最优 = 全局最优"
- ❌ "O3 贪心分 = 该局面理论最高分"
- ❌ "我们的 seed 与真游戏等价"（见 D13：**不复刻原版 RNG**；v3.0 口径是 **captured-state alignment**，只保证捕获局面的单步状态/分数一致，不保证同 seed 同局面）

**v3.0 Oracle 精确性规则**（与 03 §2.1、07 §5.2 一致）：

- `exact: true` 仅当该局面的**全部 218 个合法动作**都在真游戏中执行并记录得分；否则只能标 `exact: false`（top-k=3 + 2 个随机动作验证），报告必须写“oracle 为已验证子集最优，**不是全局最优**”。
- `best_score == 0` 的局面不进入 regret 分母，单独计数。
- O1/O2/O3 的分层不变；O3 仍只是贪心参照，**不是**该局面理论最高分。
