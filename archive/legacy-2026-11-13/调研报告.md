## 摘要

**问题**：大模型 Agent 已经能调用工具、操作界面、完成多步任务，但现有评测大多只回答"做成了没有"，无法回答"为什么没做成、错在哪一步、错在哪一类决策"。自动归因的上限也已被量化：最好方法的步级准确率只有 14.2%，通用轨迹上的模型定位只有 11%——用模型读轨迹做根因分析目前不可用。

**思路**：把评测放进一个"规则可判定、状态可复现、最优可计算"的环境。本项目选择单人卡牌 Roguelike **Balatro** 的规则子集自建确定性引擎：单步出牌组合上限 218 种、分数由确定性算术给出、随机性可由种子固定。在此基础上构造 60 个固定场景与分层 Oracle（精确局部最优 + 蒙特卡洛近似弃牌 EV），定义以 `Local Regret` 为主的指标族，并用 4 类判定器（3 类确定性：非法动作 / 算分错误 / 规则幻觉；1 类启发式：规划不足）自动归因失败，最后用配对实验与统计报告给出可复现的结论。

**调研结论**：
- 学术侧，"过程指标"目前只有估计值（AgentBoard、BALROG 的进度依赖人工标注子目标），"失败归因"的判定器全部是 LLM、金标准全部是人工标注——**没有工作把归因建立在可精确枚举的状态空间上**；
- 生态侧，Balatro 的"真游戏控制"与"算分"已成熟，"LLM 评测但只给总分"已有 Evalatro 与 balatrobench 两个项目，而"确定性环境 + 固定场景 + oracle + 归因"这个组合**截至检索日尚未有人做过**；
- 本项目的位置因此是清晰的：它不重复"谁分高"，而是回答"为什么低、低在哪类决策"，并把判定权从模型交给规则。

**关键词**：大模型 Agent；多步决策；可验证评测；失败归因；Oracle 与 Regret；Balatro


## 1 选题背景及意义

### 1.1 从"能回答"到"能行动"：Agent 评测的重心正在从结果转向过程

过去两年，大模型的能力叙事发生了明显位移：从"答对一道题"转向"完成一件事"。ReAct 把推理与动作交错生成，让"思考—行动—观察"的循环成为可复现的评测单元 [1]；随后的反思、自我修正、树搜索与树状规划，把"测试时计算"变成提升多步决策的主要手段 [2][3][5][6]。当模型开始调用工具、操作界面、写代码、做多轮对话，"它有多强"这个问题就再也不能用一道题的准确率回答。

但评测没有跟上。今天主流的 Agent 基准，绝大部分仍然只交出一个数字：WebArena 报成功率 [25]，TravelPlanner 报约束满足率 [31]，SWE-bench 报测试通过率 [34]，τ-bench 报 pass^k [24]，BALROG 报归一化进度 [52]。这些数字当然有用，但它们回答的是"**做成了没有**"，而不是"**为什么没做成、错在哪一步、错在哪一类决策**"。

这正是本研究要切入的缝隙。**如果 Agent 的失败不能被定位，那么"提升 Agent"就只能靠试错；如果失败不能被归类，那么不同模型之间的差异就只是一串不可解释的分数。**

### 1.2 三个瓶颈：不可判定、不可复现、不可归因

把现有评测的困难拆开看，是三个彼此独立、但互相放大的问题。

**第一，不可判定。** 很多真实环境（网页、桌面、GUI）的成功判据依赖脚本或人工设定，动作空间无法枚举，状态转移不可精确重放 [27][58]。于是评测只能给出"终局是否成功"的 0/1 信号，或者一个由基准作者自定义的归一化分数 [52][55]。**判据一旦不可判定，"最优"就无从定义，"差多少"也就无从计算。**

**第二，不可复现。** 真实环境受版本、网络、渲染、随机性影响；即使开源，复现实验也常失败 [81]，而机器学习研究的可复现性需要把代码、数据、种子与日志的提交制度化 [64]。强化学习社区的教训尤其直接：结果对随机种子、超参与实现细节高度敏感，单次运行的单点比较不可信 [63]；即便是确定性环境，也会被"记住序列"式的退化解利用，需要显式的评测协议（如 sticky actions）来抑制 [62]。围绕游戏环境的社区实践更直接：为了批量跑真游戏，只能靠加速 mod 把速度拉到数百倍 [110]，而整条注入链又被绑定在"游戏版本 × 注入器版本 × mod 版本"的三维矩阵上 [105]。**一个不能被第三方一键复跑的评测，其结论只能被相信，不能被检验。**

**第三，不可归因。** 这是最被忽视、也最难的一环。现有工作已经把"失败"变成可分类、可统计的对象 [86][87]，但自动归因的上限非常低：在多智能体失败日志上，最好的方法定位责任主体的准确率是 53.5%，定位**具体错误步骤只有 14.2%** [84]；在通用 Agent 轨迹上，最强模型做错误定位只有 11% [85]。**用 LLM 读轨迹做根因分析，目前基本不可用。** 与此同时，LLM-as-a-Judge 这条路也被证明靠不住：在"客观正确性"这种有唯一答案的任务上，强裁判的表现只略好于随机猜测 [67]。

三个瓶颈合起来指向同一个结论：**要得到可信的 Agent 评测结论，必须把评测放进一个"规则可判定、状态可复现、最优可计算"的环境里，并把"判定权"从模型手里拿走、交给确定性程序。** 这不是一个工程偏好，而是被文献反复证明的方法论要求 [7][16][67][84]。

### 1.3 为什么选 Balatro 作为载体

本项目选择一个具体的、规则完全显式的卡牌 Roguelike——Balatro——作为评测载体，并用其**规则子集**自建确定性环境。理由有五条，每条都有事实依据：

1. **最优值可定义。** Balatro 的计分是"牌型基础分 × joker 乘区"的确定性算术，无隐藏手牌、无对手博弈；随机性只来自抽牌与商店，而二者可由种子固定——社区已有多个工具通过离线复刻原版 RNG 来精确推演种子内容 [107][108]，说明"固定种子 ⇒ 固定牌序与商店序列"是可验证事实而非口头承诺。
2. **单步动作空间可枚举。** 在本项目的规则子集下，一次出牌的组合数上限为 `Σ C(8,k), k=1..5 = 218`，去重后通常 60–80 个。**可枚举意味着可精确求最优、可精确算 regret**；对比 Jericho 的自由文本动作 [53]、NetHack 的组合式动作 [54]、GUI 环境的坐标动作 [58]，这些环境在原理上只能采样估计。
3. **分数是确定性函数，不需要自定义口径。** BALROG 的"成功"是各游戏进度/分数的归一化组合 [52]，Crafter 是成就解锁率 [55]——这些量"可读"，但口径由基准作者定义，跨版本容易漂移。Balatro 的分数与盲注目标分可直接比对，"是否达标"是布尔事实。
4. **长程资源分配是真实难点。** 有限出牌/弃牌次数、joker 槽位、商店取舍构成"短视 vs 规划"的张力。最近的 RL 前作已经实证了这一点：把战术与战略拆成双策略后，首盲通过率可超过 99%，但**平均最大 ante 仍停在 3/8，剩余差距被明确归因于长程战略规划** [90]。这说明该环境能稳定产生"局部最优、全局失败"的失败模式——正是失败归因需要覆盖的对象。
5. **成本与可复现性可控。** 自建规则子集不需要正版游戏、GPU、注入链，可 CI、可并行、可一条命令重跑；相比之下，真游戏路线的单局成本是数十分钟且不可并行 [93][96]，RL 路线需要 512 倍加速才勉强可训练 [99][110]。

需要强调：**选 Balatro 不是因为它"好玩"，而是因为它是少数同时满足"可判定 + 可枚举 + 有长程张力 + 低成本"四个条件的载体。** 换成任何具备同样性质的环境，方法论都成立。

### 1.4 研究意义

**方法层面**：本项目把"过程指标"从估计变成测量。现有最接近的工作（AgentBoard、BALROG）用"进度百分比"刻画过程 [33][52]，而进度依赖人工定义子目标；本项目用可枚举的最优动作给出 `regret`，同一个量变成可复算的精确值。**这不是"又一个 benchmark"，而是对"过程指标能不能精确化"这一方法论问题的回答。**

**评测层面**：本项目给出一个"判定器可靠性"的报告范式——per-class Cohen's κ、95% 置信区间、混淆矩阵、弃权率。现有归因工作多报合并 κ 或总体准确率 [86][84]，会掩盖个别类别的低一致性；本项目把这一点做成硬性验收项。

**工程层面**：在 8 GB 内存、Windows 原生、无 GPU 的消费级单机上，搭建一条从 MCP 工具调用到 trace 归因再到统计报告的完整流水线，并给出"单位评测成本"这一工程指标。对"如何低成本地持续评测 Agent"这一问题，它提供可复制的样板。

**实践层面**：失败归因的产物（"哪一类失败占比最高"）直接指向优化方向。如果实验显示小模型的失败主要来自算分错误与规则幻觉、而非长程规划，那么"给它更强的规划模块"就是错误投入——**这种可操作的结论，只有可判定的归因才能给出**。

### 2.1 长程决策与规划：从"提示范式"到"可执行动作空间"

#### 2.1.1 推理—行动交织与测试时搜索

ReAct 最早把推理轨迹与环境动作交错生成，在 ALFWorld 与 WebShop 上分别比模仿学习/强化学习基线高出 34 与 10 个百分点（绝对成功率），且只用了一到两个示例 [1]。它确立了一个关键形式化：**一条可观察的"思考→动作"序列就是评测与分析的最小单元**，这也是本项目能够逐步判定合法性、逐步计算 regret 的前提。随后的 Reflexion 把试错搬到文本空间，用语言化反思加情景记忆替代权重更新 [2]；Self-Refine 在同一轮内做"生成—自我反馈—重写" [3]。这两条路线的共同点是**把改进寄托于模型自身的判断**，而这恰好是最脆弱的一环：后续对照实验显示，在推理任务上不给外部反馈的"内在自纠正"不仅无效，甚至会掉点 [16]。Tree of Thoughts 把 token 级左到右解码扩展为 thought 级的搜索与回溯，在 Game of 24 上把 GPT-4 的成功率从思维链的 4% 拉到 74% [5]；LATS 进一步把蒙特卡洛树搜索、语言模型价值函数与自反思统一起来，在 HumanEval 与 WebShop 上取得明显增益且完全免梯度 [6]。

这一脉的贡献是证明了"测试时计算可以换性能"，局限同样明确：**搜索需要环境可回滚、可重放，并且依赖一个未必可靠的"思考评估器"**。对本项目而言这恰是机会——我们的环境规则确定、状态可精确重放，因此"最优动作"是**可计算的真值**，而不是靠模型自评出来的近似值 [6][7]。

#### 2.1.2 规划的外置：分解、验证与形式化动作

Plan-and-Solve 用"先制定计划、再按计划执行"的两段式提示稳定零样本思维链 [4]，但它只解决"先想后做"的表述问题，没有解决计划是否成立。ReWOO 把规划与观测解耦，先一次性生成完整计划再批量取观测，显著降低 token 消耗 [10]；DEPS 面向开放世界任务，用"描述—解释—计划—选择"把高层目标拆成可执行子目标迭代推进 [8]；ADaPT 按需递归分解，只在子任务确实超出模型能力时才继续往下拆 [9]。三者的共同思想是：**规划质量应由子目标是否可达、是否可执行来检验**，而不是由计划文本是否好看来判断。

LLM-Modulo 把这一思想推到立场论文的高度：作者认为自回归语言模型无法可靠地做规划或自我验证，正确形态是让模型充当"通用近似知识源"，由外部基于模型的验证器做紧耦合的双向校验 [7]。这与本项目的设计哲学完全一致——我们不是在"让模型学会打牌"，而是在构造一个**外部验证器可判定**的环境，把模型的规划能力变成可核对的命题。

具身与程序化行动方向给出了另一条证据链：SayCan 用技能的价值函数（affordance）约束语言模型的提议，让"说得出"的动作同时是"做得到"的动作 [11]；Inner Monologue 把环境反馈回灌进闭环规划 [12]；ProgPrompt 把动作空间写成带前置条件的函数签名，使"计划"直接成为可静态检查的程序 [13]；Voyager 把这一思路推到极致，用自动课程加不断增长的可执行代码技能库，在 Minecraft 上取得数倍于基线的探索效率 [14]。这一脉最重要的启示是：**一旦动作被形式化为有限、带前置条件的操作集合，合法性就从"感觉合理"变成"可判定"**；Voyager 的自验证之所以有效，也是因为它验证的是执行结果与执行错误，而不是模型对自己的评价 [14][16]。

#### 2.1.3 评测基准谱系：从"终局成功率"到"过程指标"

长程能力必须有环境来测。现有基准可以按"判定信号"排成一条谱：

| 基准 | 领域 | 判定方式（成功信号） | 是否给出过程指标 | 是否支持失败归因 |
|---|---|---|---|---|
| AgentBench [23] | 8 类交互环境 | 任务成功率 | 部分（分环境子分数） | 否 |
| WebShop [29] / GAIA [30] | 购物 / 通用助手 | 终局匹配 / 精确答案 | 否 | 否 |
| WebArena / VisualWebArena [25][26] | 真实网站 | 功能正确性（终局状态） | 否 | 否 |
| OSWorld [27] | 真实操作系统 | 脚本化终局检查 | 否 | 否 |
| ALFWorld [28] / ScienceWorld [60] | 文本化具身 / 科学实验 | 任务完成 / 0–100 分 | 否 | 否 |
| TextWorld [59] / ALE [61] | 程序化文本游戏 / Atari | 通关或得分 | 否 | 否 |
| MineRL [56] / MineDojo [57] | Minecraft | 奖励或里程碑计数 | 否 | 否 |
| τ-bench [24] | 工具—用户对话 | 数据库终态比对 + pass^k | 部分（pass^k 稳定性） | 否 |
| TravelPlanner [31] | 多约束行程规划 | 约束满足率 | 部分（约束分类统计） | 部分（人工归因失败类型） |
| PlanBench [32] | 经典规划域 | 计划可执行/正确 | 否 | 否 |
| AgentBoard [33] | 多轮交互 | 成功率 + progress rate | **是**（进度估计） | 否 |
| BALROG [52] | 多款游戏 | 归一化进度/分数 | **是**（细粒度进度） | 否 |
| SWE-bench [34] | 真实代码仓库 | 单元测试通过 | 否 | 否 |
| **本项目** | Balatro 规则子集 | **相对 oracle 的 regret + 盲注达标 + 4 类判定器** | **是（精确值）** | **是（确定性证据链）** |

这张表的关键读法是两列：**"是否给出过程指标"一列只有 AgentBoard [33] 与 BALROG [52] 是肯定的，而两者的 progress 都依赖人工或模型标注的子目标分解，本质是"离终点多远"的估计值；"是否支持失败归因"一列除 TravelPlanner（人工归因失败类型）与本项目外，其余全部为否。** 也就是说，评测社区的成熟度集中在"把成功定义成一个能算的数"，而"把失败拆成可判定的原因"这一层基本是空的。

具体数字也说明问题：WebArena 上最佳 GPT-4 agent 端到端成功率仅 14.41%，人类为 78.24% [25]；TravelPlanner 上 GPT-4 的成功率只有 0.6%，失败集中在"跑题、工具选错、多约束跟踪不住" [31]；SWE-bench 发布时最强模型只能解决 1.96% 的 issue [34]；τ-bench 里即便是函数调用能力很强的模型，任务成功率也不到 50%，零售域的 pass^8 低于 25% [24]。这些数字常被引用为"Agent 还很弱"，但真正值得注意的不是弱，而是**我们只知道它弱，不知道它弱在哪一步、弱在哪一类决策**。

#### 2.1.4 实证发现：可靠性比能力更差，错误有结构

第一，**失败随步数累积**。AgentBench 在 8 个环境中系统测试后指出，商用模型与不超过 70B 的开源模型差距显著，且失败主因被归为"长程推理、决策与指令跟随能力不足"，而非单点知识缺失 [23]；TravelPlanner 的失败分析同样指向"保持任务不跑偏、选对工具、同时跟踪多个约束"这三类长程症状 [31]。

第二，**pass@k 会系统性高估可靠性**。τ-bench 用 pass^k（k 次独立试验全部成功）揭示：单次成功率接近 50% 的模型，pass^8 可以低到 25% 以下 [24]。**"会做"与"稳定会做"是两件事**，而多数基准只报前者。

第三，**上下文与记忆是独立瓶颈**。Lost in the Middle 发现模型对长上下文中部信息的利用显著劣于首尾（U 型）[15]，这直接威胁任何"把完整历史塞进 prompt"的评测设计；Reflexion 与 Voyager 之所以有效，很大程度上是因为它们把历史压缩成了反思文本或技能库，而不是把全部轨迹塞回上下文 [2][14]。

第四，**自纠正不是免费的**。无外部反馈的内在自纠正会掉点 [16]，LLM-Modulo 也主张模型不能可靠自验证 [7]。这从反面证明了本项目的方法论前提：**判定权必须交给环境，而不是模型**。

第五，**失败本身是可分类、可统计的对象**。MAST 对多智能体系统的失败做了系统归纳，从跨框架轨迹中提炼出 14 个失败模式并聚为 3 大类，报告标注者间一致性 κ = 0.88 [86]；AgentDebug 进一步给出模块化错误分类学（记忆/反思/规划/行动/系统五层）与配套标注集 [87]。这说明"失败类型"可以像指标一样被测量——前提是分类学设计得足够可操作。

#### 2.1.5 训练侧：可验证性同时定义了奖励与评测

过程奖励模型的经典结论是：对每一步给反馈的过程监督显著优于只对结果给反馈的结果监督，并公开了大规模步级人工标注 [17]。这与本项目的 oracle 判定器在形式上高度同构——**逐步可判定的环境天然能生产步级标签**，只不过我们的标签来自规则引擎而不是人工。

可验证奖励（RLVR）路线表明，当奖励信号可以由确定性验证器给出时，纯强化学习就能显著提升多步推理能力 [18]，其成功概率的理论刻画也已被给出 [19]；在 Agent 场景，WebRL 用自演化在线课程做 web agent 训练 [20]，ArCHer 把多轮交互建模为分层强化学习以处理轨迹级信用分配 [21]，FireAct 则证明少量高质量轨迹微调即可显著改善 agent 行为 [22]。

这些工作对本项目的意义是双向的：一方面，"确定性验证器 + 轨迹级信号"已是当前训练侧的主流基础设施，我们的环境可以直接复用为 verifier；另一方面也提示了一个评测风险——**当一个确定性环境被用作训练奖励时，模型可能学到的是这个环境的规则细节，而不是可迁移的规划能力**，因此评测必须使用 held-out 的规则变体或参数扰动 [18][20]。

#### 2.1.6 牌类博弈：从"竞技求解"到"能力评测"的转身

牌类是 Agent 研究的老战场，但传统目标是"打败人"，而不是"评测人"。不完全信息博弈的算法主线是反事实 regret 最小化（CFR）家族：它证明最小化反事实 regret 即最小化整体 regret，从而自博弈收敛到 Nash 均衡 [37]，此后十余年仍在演进 [38]，并在工程上产出三个里程碑——一对一无限注德州扑克击败顶级职业选手 [39]、超人水平扩展到六人桌 [40]、限注单挑被"完全求解"并给出可利用度上界 [41]；综述文献系统整理了该领域的抽象、求解与评测口径 [42]。牌类动作空间随局面剧烈变化是核心难点，斗地主与麻将分别用深度蒙特卡洛、全局奖励预测加 oracle guiding 给出了解法 [43][44]；纯合作的 Hanabi 把"推断他者意图"推到前台 [45]，桥牌则形成"与固定强 bot 搭档评测"的惯例 [46][47]。工程基础设施上，OpenSpiel 与 RLCard 把上述博弈统一成同一套 API，提供精确博弈树遍历、最佳响应与可利用度计算 [48][49]。

这一传统给了本项目两个可直接借用的基座：**用 regret / 可利用度而不是胜率来度量策略质量** [37][41][48]，以及**用统一环境 API + 精确博弈树保证评测可复算** [48][49]。但也要注意其反面：这些工作都把"牌"当作**要打败的对手**，没有一个把牌类游戏当作**诊断 Agent 推理失败的探针**。

真正把卡牌游戏用于 LLM 能力评测是 2025 年前后才成形的方向：有工作在八款卡牌游戏上系统评估 LLM，发现"经高质量对局数据微调后可接近强游戏 AI，但掌握复杂游戏会损害通用能力" [50]；lmgame-Bench 则从方法论上指出"直接把 LLM 丢进游戏"不构成有效评测（视觉感知脆弱、提示敏感、数据污染），需要统一 API、轻量脚手架与防污染设计 [51]。这两条恰好标出本项目的位置：**卡牌 + LLM 的评测已被认为有意义，但现有做法仍以分数/胜率为终点，没有回答"它为什么输"。**

### 2.2 自动判定与自动评测：判定权交给谁

#### 2.2.1 可验证 / 规则化判定

这一支的共识是**把评测信号从"文本相似"换成"可执行判定"**。HumanEval 用单元测试判功能正确性，并给出 pass@k 的无偏估计量 [35]；SWE-bench 把判分交给仓库自带的测试，用两千余个真实 GitHub issue 逼出"改多文件 + 与执行环境交互"的长程行为 [34]；SQuAD 则把 exact-match / F1 这套"参考答案匹配"范式做到极致，也暴露了它的天花板——答案必须能被字符串规范化对齐 [36]。τ-bench 更进一步，把判分做成"对话结束后比对数据库终态与标注目标态" [24]。

这一支的指标（成功率、pass@k、EM/F1、状态比对）都是**可精确复算**的量，正是本项目要复用的部分。局限有三：测试/答案集本身由人写，写错就错判；判分粒度停在 episode 级（成功/失败），不回答"哪一步错"；且容易被刷穿——holdout 不足会被 agent 用 shortcut 利用 [79]。

#### 2.2.2 LLM-as-a-Judge

MT-Bench / Chatbot Arena 是这一支的奠基工作：用强模型当裁判，在数千条专家投票与数万条人类偏好对话上验证裁判与人类的一致率，同时系统列出位置偏差、冗长偏差、自我增强偏差与推理能力不足 [65]。G-Eval 把裁判做成"思维链 + 表单填空"的评分流水线 [66]；综述文献进一步把"如何构建可靠裁判"整理为一致性、偏差缓解与场景适配三条主线，并强调需要标准化 [70]。偏差随后被做成"攻击面"：仅调换两个回答的出现顺序，就能让较弱的模型在多数 query 上"击败"强模型 [68]；自我偏好则被追溯到"自我识别"能力——模型能以非平凡准确率认出自己的输出，且自我识别能力与自我偏好强度呈线性相关 [69]。

可靠性侧有三条关键结论：

- **JudgeBench** 用"客观正确性"构造难度对，发现包括 GPT-4o 在内的强裁判只略好于随机猜测——**以人类偏好为金标准会高估裁判** [67]；
- **Trust or Escalate** 给出另一条路：让裁判输出置信度并"选择性评估 + 逐级升级"，可以在指定一致率水平上给出可证明的人类一致率保证 [71]；
- **The Leaderboard Illusion** 从制度侧证明，即使是靠人类投票的公开排行榜，私有测试、选择性披露与采样不对称也会系统性扭曲排名 [72]。

**对本项目的直接结论：裁判可以作为"解释器/归因辅助"，但不能进主指标；且裁判自身必须被单独评测（一致性、偏差探针、弃权率），否则只是一层不可审计的噪声。** 这条主张的证据三角是 [67]（裁判在客观正确性上不可靠）、[85]（轨迹级定位仅 11%）、[84]（步级归因仅 14.2%），详见 2.3 节。

#### 2.2.3 轨迹级 / 过程级评测

过程监督是这条线的起点：用大规模步级人类标注训练过程奖励模型，使过程监督显著优于结果监督 [17]。Agent 侧则把"过程"从推理步扩展到工具调用步：Agent-as-a-Judge 让 agent 去评 agent，在真实开发任务上给出中间反馈 [73]；AgentBoard 用 progress rate 把 episode 切成可比较的推进度 [33]；AgentEval 走"先按应用目的自动生成评判准则，再量化 utility"的路线 [74]。

轨迹级评测真正的困难在**错误定位**：TRAIL 建立了 agentic trace 的错误分类学并发布人工标注轨迹，结果是最强的模型在 trace debugging 上只有 11% [85]；AgentRewardBench 用一千余条经专家复核的 web agent 轨迹评了 12 个自动裁判，发现没有任何一个裁判在所有基准上都好，且常用的规则判分**低报**成功率 [75]。多智能体侧，MAST 从上千条轨迹归纳出 14 个失败模式、报告 κ = 0.88，并训练了一个与人工高度一致的自动标注器 [86]。

这一支的共同短板是：**金标准是人工标注，成本高、规模小（百余条到千余条量级），且评测对象是"判定器与人类的一致性"，而不是"判定器与可复算真值的一致性"**——这恰好是本项目想换掉的假设。

#### 2.2.4 评测效度：指标之外的元问题

评测效度本身已经成为研究方向：HELM 确立了"多指标 × 多场景 × 标准化"的报告范式 [76]，BIG-bench 用大规模众包任务集证明任务多样性的价值，并区分"性能随规模平滑提升"与"在临界规模突变"两种曲线 [77]。在此之上，有五条经验教训值得逐条记住：

- **污染**：仅做 n-gram 匹配的去污染不够，同义改写/翻译即可绕过；实测主流预训练数据与代码基准存在可观重叠 [78]。
- **成本**：AI Agents That Matter 指出 agent 基准只盯准确率，导致对"精度来自哪里"得出错误结论，并额外指出 holdout 不足与评测不可复现两个系统性问题，主张把 cost 与 accuracy 联合优化 [79]。
- **统计**：评测应被视为从超总体抽样的实验，报告置信区间与差异检验，而不是只报点估计 [80]。
- **可复现**：对大量论文的手工复现实验表明，"放出代码"不等于"可复现" [81]；机器学习研究的可复现性需要把代码、数据、种子与日志的提交制度化 [64]。
- **Goodhart 风险**：reward hacking 有形式化定义——只有当代理指标的期望回报上升永不会降低真实回报时，该指标才叫不可被刷，而这一条件在全部随机策略集合上几乎只有常数奖励满足 [82]；奖励模型过优化的缩放律则给出"优化越狠、真实分数先升后降"的函数形式 [83]。

这五条共同构成一张**必须报告的清单**：主指标要给置信区间、要报成本、要做污染与 holdout 检查、要固定版本与随机性、要论证指标为何不易被刷。本项目的"exact / approx"标注与预注册制度，正是对这张清单的逐条回应。

### 2.3 失败归因

#### 2.3.1 问题定义

"失败归因"要回答的不是"得了多少分"，而是"**哪个决策、哪个环节、因为什么原因导致了失败**"。它比评测难一个量级，因为它要求把"结果"反推到"过程"，而过程往往是隐式的、多因的、且存在错误传播。

#### 2.3.2 三条技术路线及其上限

**路线一：让 LLM 读轨迹做判定。** 代表是 Who&When：它把"哪个 agent、哪一步该为失败负责"形式化为新任务，发布上百个多智能体系统的失败日志与细粒度标注，并评测三类自动归因方法。结果是：最好的方法在 agent 级只有 53.5% 准确率，在**步级只有 14.2%**，部分方法甚至低于随机，即便推理能力最强的模型也达不到可用水平 [84]。TRAIL 在通用 agentic trace 上得到同样的结论：最强模型仅 11% [85]。**这组数字是整块领域最重要的事实——用 LLM 读轨迹做根因定位，当前基本不可用。**

**路线二：先建分类学，再配数据管线。** MAST 把失败模式做成可统计、可标注一致的对象（14 模式 / 3 大类，κ = 0.88）[86]；AgentDebug 建立五层模块化错误分类学与配套标注集，并用"隔离根因 + 给纠正反馈"的调试框架把 all-correct 准确率提升 24%、步级准确率提升 17% [87]。这证明**分类学加数据管线比单点提示更有效**，但判定仍由模型完成，因此仍受路线一的上限约束。

**路线三：因果与信用分配。** 有工作把 Shapley 合作博弈归因与过程奖励模型结合：成功时用 Shapley 把系统级结果分摊到各 agent 与消息，失败时用"首次错误定位"构造修复感知的偏好信号 [88]；但作者明确声明这是概念性工作、**实证验证留给未来**。**错误传播**方向则把多智能体流水线中的错误演化建模成状态转移过程，实测每道边界的逃逸概率逐级上升（约 24.6% → 48.3% → 89.3%），而"在边界处设闸门"能把错误存活率从 58.4% 降到 16.2% [89]。它给本项目的启示很具体：**归因不只回答"谁错了"，还要回答"错在第几个状态转移上、还能不能被抓到"**。

#### 2.3.3 为什么现有路线到不了"确定性"

把三条路线放在一起看，缺口很清楚：

| 维度 | 现有工作 | 本项目 |
|---|---|---|
| 判定主体 | LLM（读轨迹、给标签） | **规则引擎（重放、比状态）** |
| 金标准 | 人工标注（百余至千余条） | **可枚举动作集与精确分数（可无限生成）** |
| 结果形态 | 类别标签 + 自然语言理由 | 类别 + `rule_id` + `state_hash` + 最小反例 |
| 可信度证据 | 与人工标注的一致性（accuracy / κ） | 与人工标注的一致性 **且** 判定器幂等性与可复算性 |
| 类别与指标的耦合 | 弱（类别无法换算成分数损失） | **强（每类都可换算成 regret 或合法性损失）** |
| 规模瓶颈 | 人工标注成本 | 无（场景可程序化生成） |

换言之：**归因领域缺的不是"更好的分类学"，而是"一个判定基准"**——一个状态与动作可精确枚举、因而可以把"根因"定义成可计算命题的环境。这正是本项目选择 Balatro 规则子集的根本理由，而不是因为"卡牌游戏好玩"。

#### 2.3.4 对本项目判定器设计的直接约束

1. **判定权必须在环境侧**：模型只能输出动作与自然语言，判定由规则重放完成；模型自评不作为任何结论依据 [16][67][84]。
2. **类别必须绑定可观测证据**：每个失败类别要写清"触发条件 → 证据字段 → 什么情况不算"，否则标注一致性会崩塌 [86][87]。
3. **必须报 per-class 一致性与置信区间**：现有工作多报合并 κ 或总体 accuracy，会掩盖个别类别的低一致性；本项目按类报告 Cohen's κ 与 95% CI，并给出混淆矩阵与弃权率 [80][86]。
4. **启发式类别必须显式降级**：允许判定器输出"证据不足"或"疑似"，并把低置信样本转入人工复核，而不是强行归类 [71][75]。

### 2.4 Balatro 生态的现有项目

Balatro 是 2024 年发布的单人卡牌 Roguelike：用扑克牌型出牌得分，靠 joker 与消耗牌改造收益，在有限出牌/弃牌次数内达到盲注目标分。它的规则完全显式、无隐藏手牌、无对手博弈，随机性只来自抽牌与商店，而这两者可由种子固定——这使得"每一步的分数"原则上可精确计算。

围绕它已经形成一个不算小、但**高度"打牌导向"**的生态。按功能可以分为五层，下面逐层介绍（引用编号见第 8 章 G 组；各项目的规模与活跃度以 2026-11-12 的公开页面读数为参考）：

| 层 | 代表项目 | 解决的问题 | 与本项目的关系 |
|---|---|---|---|
| 控制层 | balatrobot [93]、balatrollm [94]、Steamodded [104]、Lovely [105] | 让程序读状态、发动作、改规则 | 借鉴接口语义，不引入依赖 |
| 评测层 | Evalatro [96]、coder/balatrobench [95] | 让 LLM 玩真游戏并排行 | 定位对照，不重复其工作 |
| 环境层 | balatro-gym [98]、Balatro-Gym [99]、balatro-rs [97] | 给 RL/Agent 一个可调用的环境 | **balatro-rs 是最接近的自建引擎** |
| 求解层 | EFHIII calculator [101]、Balatro-Simulation [102] | 精确/近似算分，求最优打法 | **Local Oracle 的设计参照** |
| 数据层 | Balatro HQ [108]、Wiki [109]、Immolate [107] | 种子推演、规则数据、清单 | 对拍与数据核对来源 |

#### 2.4.1 控制层：把真游戏变成可编程接口

**`coder/balatrobot`**[93] 是这个生态里最重要的一块基础设施。
- **目的**：给正版 Balatro 一个程序化控制面，让外部 Bot / RL / LLM 能读全量状态并执行动作。
- **设计原理**：以 Lua mod 注入游戏后在本机启动 HTTP 服务，采用 **JSON-RPC 2.0，默认端点 `127.0.0.1:12346`**，共 22 个方法（`health / gamestate / start / select / play / discard / buy / sell / reroll / cash_out / next_round / use / add / set / screenshot` 等），每个方法声明**前置状态**（如 `play` 必须在选牌阶段）并返回统一错误码（`BAD_REQUEST / INVALID_STATE / NOT_ALLOWED / INTERNAL_ERROR`）；状态机为 `MENU → BLIND_SELECT → SELECTING_HAND → ROUND_EVAL → SHOP → GAME_OVER`。`gamestate` 返回结构化对象（手牌、joker、消耗牌、商店、凭证、卡包，均为带数量上限的"区域"结构）。
- **效果**：它已成为"真游戏控制"的事实标准，被 Evalatro 等直接复用，并提供 OpenRPC 描述与面向 LLM 的文档；但它必须拥有 Steam 正版游戏与完整注入链，有图形界面依赖，一局到后期需数十分钟，**无法批量并行**。
- **与本项目关系**：不直接复用，但**接口设计要"借鉴型照抄"**——"方法 + 前置状态校验 + 统一错误码"几乎可以一一映射到我们的 MCP 工具契约；其状态字段分层可直接作为场景快照 JSON 的参考。唯一不借鉴的是它用"手牌下标"表示动作，因为下标在手牌重排后不可复现。

**`coder/balatrollm`**[94] 是官方参考 LLM bot：分析状态 → 决策 → 通过 balatrobot 执行循环。
- **效果**：它是"LLM 打 Balatro"的事实基线，也是下游排行榜的数据来源；但它是**生成式 bot**，目标是把牌打好，不产出评价与归因。

**`Steamodded/smods`**[104] 与 **`Lovely` 注入器**[105] 构成 mod 生态底座（前者提供 joker/盲注/牌型的对象体系与 `calculate(context)` 回调，后者提供不修改游戏文件的运行时注入）。
- **效果**：它们让"改规则"变得容易，也给出了一份**社区公认的规则语义描述**（一个 joker 在什么阶段、对哪些卡、以什么顺序生效）；代价是**整条链被绑定在"游戏版本 × 注入器版本 × mod 版本"的三维矩阵上**，任何评测框架一旦依赖它，可复现性就无从谈起 [105]。

**`balamod`**[106] 是另一条已停更的注入/反编译路线，进一步说明这条路线内部并不统一。

**`HandyBalatro`**[110] 则是一个 QoL 加速 mod，被 RL 环境用来把 rollout 提速到 512 倍——它从侧面证明：**用真游戏做批量评测，第一瓶颈是速度，社区只能靠打补丁**。

#### 2.4.2 评测层：已经有"LLM 打 Balatro"的公开基准

**`alesha-pro/evalatro`**[96] 是**与本项目定位最接近、也最需要划清边界**的项目。
- **目的**：把真实 Balatro 变成一个可重复的 LLM 基准，模型通过 balatrobot 玩真游戏，每次决策落盘，终局给 0–100 分并上公开排行榜。
- **设计原理**：完整栈为"Steam 正版 + Lovely + Steamodded + balatrobot + 本仓库 runner"；记分公式为

```text
progress = 天梯位置 / (目标 Ante × 3) + 失败盲注的部分筹码credit
legality = 1 − 非法动作数 / 总动作数
score    = round(progress × legality × 100, 1)
```

&emsp;&emsp; 目标设为打过 Ante 12（原版 Ante 8 胜利只算里程碑）；为防止作弊，**服务端用 transcript 重算分数**、拒绝不可能轨迹、按稳定 run hash 去重、并用 code hash 打"official / community"标签；工具注册表同时服务 LLM runner 与 MCP server，保证动作面单一事实源。
- **效果**：它已经交付了"真实环境 + 公开榜 + 可回放 + 可重算"的完整闭环，是本项目在**评测产品形态**上最值得对标的对手。但它有四个明确局限：
  - 只输出**一个总分**，`legality` 只是非法动作**计数**，不分类、不定位；
  - 没有 oracle，也没有"最优动作"真值，因此**无法计算 regret**；
  - 目标是最长局，单局成本高；
  - 强依赖游戏本体与注入链，CI 不可行。

**`coder/balatrobench`**[95] 自述为"对 BalatroLLM 对局记录做基准分析并生成排行榜的工具"——解析 runs 产物、生成静态站点与排行榜、数据同步到公开数据集。**它做的是评测结果的展示与横向比较层，不定义环境、不计算最优值、不做失败归因**。

**`proj-airi/game-playing-ai-balatro`**[100] 走的是另一条路：不碰游戏内存，用视觉模型检测卡牌与 UI、用 OCR 读文字，再交给 LLM 决策。
- **效果**：它证明"视觉接地"可行，但成本高、误差源多，而且**完全不可判定**——无法区分"识别错一张牌"与"决策错一步"。它是本项目最有力的反例：**要做可判定归因，必须拿到结构化状态，而不是截图。**

#### 2.4.3 环境层：离"自建引擎"最近的一块

**`cassiusfive/balatro-gym`**[98] 提供 Gymnasium 接口，但其 README 中 **Observation / Action / Reward 三节正文均标注 WIP**——MDP 三要素未定型，接口随时可能变。这与既有规划中"**探针已取消**（其 MDP 三要素仍为 WIP，集成风险高于收益）"的判断一致。

**`Jonathanace/Balatro-Gym`**[99] 不自己实现规则，而是通过 balatrobot 驱动**活的游戏客户端**做 rollout，并借助加速 mod 把速度拉到 512 倍。
- **效果**：它给出了一个宝贵的经验数据点——**真游戏 + API 路线必须靠 512 倍加速才勉强可训练**，而这还是在不做图形渲染优化、只加速动画的前提下。

**`evanofslack/balatro-rs`**[97] 是本次调研中**最重要的新发现**：它是公开世界里最接近"自建规则引擎"的实现。
- **目的**：一套可离线运行的 Balatro 工具箱，包括规则引擎、动作生成器、存档解析与**逐字节复刻原版种子/RNG**。
- **设计原理**：Rust workspace 分层（核心引擎 / 类型 / 存档编解码 / 种子 / CLI+TUI / PyO3 绑定），核心 API 是 `gen_actions()`（穷举当前全部合法动作）与 `gen_action_space()`（**固定大小的二值动作掩码**，给强化学习用稳定形状）；覆盖牌型与计分、出牌/弃牌/重排、盲注胜负、金钱利息、商店买卖、增强/版本/印章、Boss 盲注、凭证，**joker 覆盖 74/150**，明确缺跳盲标签、其他牌组与其他赌注；附 replay 录制与离线算分。
- **效果**：它证明了"离线、确定、可枚举动作、可绑 Python"在工程上完全成立；但它**是库不是评测框架**——没有固定场景集、没有 oracle 最优动作、没有失败分类、没有 MCP 工具层、也没有与真游戏的公开对拍报告；且**未声明开源许可证**，法律上不可直接复用。
- **与本项目关系**：设计上最值得对标，四件事可直接借鉴——穷举动作生成器、固定大小动作掩码、逐字节 RNG 复刻、以及"引擎与评测器分语言时用绑定桥接"；但代码必须独立重写。

#### 2.4.4 求解层：算分器与"三态随机"的启示

**`EFHIII/balatro-calculator`**[101] 是社区标杆：输入手牌、joker、牌型等级等，算出**最高分打法**及其得分。它是纯前端交互式网页，社区引用最多，README 自述"少数 joker 可能算得不对"。
- **与本项目关系**：不集成，作为**第三方抽检参照**（抽 5–10 例基础牌型与常见 joker 组合），为"我们的 oracle 没错"提供外部证据。需要指出的是，生态里常被并列提到的 `WilsontheWolf/balatro-calculator` 经核对是它的一个 0 星 fork，并非独立实现——报告不应把两者当成两个项目。

**`DivvyCr/Balatro-Simulation`**[102] 是本次调研中**对 Local Oracle 最有直接启发**的项目。
- **目的**：在游戏内**无副作用地模拟"这一手会得多少分/多少钱"**。
- **设计原理**：把每张 joker 的 `calculate(self, card, context)` **裁剪成纯计算函数**，按 `context.cardarea`（出牌区 / 手牌区 / joker 区）与阶段（`before` / `individual` / `repetition` / `global`）分派；提供 `add_chips / add_mult / x_mult / add_dollars` 等原子算子；对随机触发的 joker 用**三态 `{min, exact, max}`** 表达而非单点值；只覆盖"影响单次出牌分数/金钱"的 joker。
- **效果**：它被同作者的实时预览 mod [103]（160 星）消费，说明"玩家真的需要算分"。
- **与本项目关系**：**设计上强烈借鉴**——效果按"区域 × 阶段"分派的组合模型可直接映射成我们的 effect 解析器；随机性用三态表达比单点值更诚实，也天然对应"确定性判定器"的输入；"只模拟影响分数的效果"这一裁剪原则，正是我们规则子集边界该采用的收口方式。但它是 GPL-3.0 且依赖游戏运行时，**只能借鉴设计，不能拷实现**。

#### 2.4.5 数据层与种子：确定性已有工程背书

- **`SpectralPack/Immolate`**[107]：用 GPU 暴力搜索"满足条件的种子"，把原版 RNG 与商店/补充包生成逻辑用 C + OpenCL 重写。它的存在本身就证明"**种子内容可以离线精确推演**"。
- **`Balatro HQ`**[108]：社区完成度最高的种子分析站，自述"逐 ante 重放游戏真实 RNG"，列出商店队列、Boss、凭证、补充包，另有算分器与 278 条数据库（150 jokers / 52 consumables / 32 vouchers 等），对齐游戏 1.0.1o。
- **`balatrowiki.org`**[109]：社区 Wiki，518 篇文章，标注对齐版本 1.0.1o，许可为 CC BY-NC-SA——**规则数值可作事实来源，描述文本必须自行改写**。
- **`jie65535/awesome-balatro`**[111]：生态全量清单，按 Tools / Mod Loaders / Mods / Resources 分类，是"有没有同类工作"的检查表。

#### 2.4.6 学术侧：Balatro 刚刚起步，且恰好印证本项目的空白

这是本节最需要精确表述的地方。**截至 2026-11-12，未发现以 Balatro 为对象、正式发表于机器学习/游戏 AI 主会或期刊的论文**（唯一已接收的是一篇 workshop 论文，见下）；arXiv 全库检索仅两条命中：

1. **Periasami 等《Reinforcement Learning for the Game of Balatro: A Fast Simulator and Two-Policy Training Approach》**（arXiv:2610.39049，已被 EXAG 2026（AIIDE Workshop）接收）[90]。
   - **目的**：为 Balatro 提供可训练的快速模拟器与 RL 基线。
   - **设计原理**：Rust 高速模拟器（用 balatrobot 对真实客户端做 state-diff 校验）、动态合法动作掩码、把决策拆成"盲注战术策略 / 商店战略策略"两个 PPO 策略。
   - **效果**：首盲通过率超过 99%，但**平均最大 ante 只收敛到 3/8**，作者把剩余差距明确归因于**长程战略规划**；论文自述"Balatro 上已发表的 RL 结果仍然稀少"，并指出三大难点——约 3000 个状态相关动作、数百步决策且奖励稀疏、抽牌与商店生成随机。
   - **与本项目关系**：这是最直接的前作。它证明了环境工程可行、任务难度真实，但它用的是**训练曲线**而非 oracle regret，也**没有自动失败归因**——恰好把"可判定评测 + 归因"这块留给了我们。
2. **Che 等《DemoEvolve: Demonstration-Guided Harness Evolution under Sparse Feedback》**（arXiv:2605.24539）[91]：把 Balatro 与另一款卡牌游戏作为长程稀疏反馈的评测环境，在 **held-out seeds** 上报告"封顶轮次进度"的提升。它把 Balatro 当**评测床**而非研究对象，且**只报标量进度，不做失败归因**。

此外还有一条**非同行评议**材料：Zenodo 上 2026-10 的课程研究提案《Jokers in the Machine: Evaluating RL vs. LLM Agent Reasoning in a Complex Roguelike Card Game》[92]，提出扩展开源环境、训练 PPO 并与提示式 LLM Agent 对比，主张"超越胜率"的指标。它证明**社区已经在想同一件事**，但只是提案，无实验、无结果、无代码——报告中只能作为"研究动向"引用，不能当作已有成果。

#### 2.4.7 "只判断不生成"的小模型方案：存在，但只能借方法论

生态里确实存在一类"不生成文本、只对给定选项给出校准概率"的判别式模型方案（TypeSafe 的 Jev / "System One"）。有个人开发者在博客中记录了把它接入 Balatro 的完整架构：`balatrobot JSON-RPC → Python 控制环（手牌评估器枚举候选并预打分）→ 模型做 choice → 执行动作`，并且**模型永远看不到原始卡牌对象和全部 218 种组合，只看到 8–15 个"已预打分的候选"**；另有一个硬编码的"恐慌过滤器"（最后一手且还有弃牌、最佳估算远低于需求时，强制只给弃牌选项）。
- **效果**：**Jev 官方没有公开的 Balatro 集成仓库**（另有第三方 benchmark 仓库，非官方产物）、没有对照实验、没有任何量化结果，作者自己指出最大瓶颈是"算分近似"。
- **与本项目关系**：**方法论直接借鉴、模型坚决不引入**。可借鉴三条：
  - "精确计算归代码、判断归模型"的分工；
  - 给模型"已预打分的候选集"而非原始状态（既降 token 又消除非法动作）；
  - 用规则守卫兜住模型的系统性错误。不引入的理由：闭源云 API、与"评测而非打牌"的目标相反、且会让项目从评测框架漂移成打牌优化。

#### 2.4.8 生态小结

把上面的项目按"能不能支撑可判定归因"重新排一遍，会得到一个很干净的结构：

| 能力 | 生态现状 | 缺口 |
|---|---|---|
| 读状态 / 发动作 | 成熟（balatrobot 栈） | 依赖正版游戏与注入链，不可 CI |
| 精确算分 | 成熟（calculator / simulation / 种子推演） | 交互式或局部，**无可编程 oracle API** |
| 完整规则引擎 | 存在（balatro-rs） | 无 license、覆盖不全、**无场景集与最优值** |
| LLM 评测 | 存在（Evalatro / balatrobench） | **只给总分，无 regret、无归因** |
| 固定场景集 | **无** | 全是整局或整种子 |
| 失败归因 | **无** | 非法动作只计数不分类 |
| 规则一致性基准 | **无** | 各实现覆盖互相矛盾 |

### 2.5 综合差距分析：本项目的空位在哪里

把学术侧（2.1–2.3）与生态侧（2.4）叠在一起，可以清楚地看到四层空位：

**空位一：过程指标只有"估计值"，没有"测量值"。** \
AgentBoard 的 progress rate [33] 与 BALROG 的细粒度进度 [52] 已经把"过程"当一等公民，但二者的进度都依赖人工或模型标注的子目标分解，本质是"离终点多远"的估计。而在一个动作可枚举、分数可精确计算的环境里，同一个量可以变成**测量值**：最优分是多少、你得了多少、差多少，全部可算且可复算。这是本项目最硬的方法论差异点，而不是"我们也做了一个 benchmark"。

**空位二：失败归因的判定基准是空的。** \
现有归因工作的判定器都是 LLM、金标准都是人工标注，而两条上限数字非常刺眼：Who&When 步级 14.2% [84]、TRAIL 11% [85]。同时，分类学工作（MAST [86]、AgentDebug [87]）已经证明"分类学 + 数据管线"有效，但**没有人把归因建立在可精确枚举的状态空间上，用规则重放给出确定性、可审计的根因与最小反例**。这是本项目唯一真正稀缺的部分。

**空位三：归因类别与量化指标没有耦合。** \
MAST 是系统级、AgentDebug 是模块级、TRAIL 是通用 trace 级，三者的类别都无法直接换算成"分数损失"。而本项目的 4 类失败直接挂在 Local Regret 与 Action Optimality 上，使"失败类型 → 指标损失"可换算、可排序、可做成本收益分析。

**空位四：Balatro 生态里，"环境 + 场景 + oracle + 归因"这个组合截至检索日尚未有人做过。** \
评测侧最强的 Evalatro [96] 只给总分，引擎侧最强的 balatro-rs [97] 只是库，学术侧唯一的前作 [90] 用训练曲线。**截至 2026-11-12 的公开检索，未发现把四件事合在一起的项目**；而"确定性子集 + 固定场景 + 精确 oracle + 确定性判定器"恰好是 100 小时单人预算内做得完的组合。

## 3 研究内容

### 3.1 研究问题

本项目不追求"让 Agent 把 Balatro 打得更好"，而是把 Balatro 当作一把**刻度已知的尺子**，回答四个可检验的问题：

| 编号 | 研究问题 | 可检验形式 | 对应产出 |
|---|---|---|---|
| **RQ1** | 能否用一个**规则子集**构造出"既有长程性、又能精确判分"的 Agent 评测环境？ | 规则引擎与真实游戏在 25 个人工取样局面上分数一致率 100%；同 seed 重跑状态序列与分数完全一致 | WP1 规则子集引擎 |
| **RQ2** | 基于 oracle 的**局部 regret** 能否稳定区分模型/提示差异，而不依赖通关率？ | 三组配置在 60 个场景上的 Local Regret 分布可区分；Random 基线与 Greedy-Oracle 基线分别落在两端 | WP2 评测集 + WP3 指标 |
| **RQ3** | 失败能否被**确定性判定器**自动归类，且与人工标注保持可用的一致性？ | 4 类判定器在同一 trace 上两次运行输出完全一致（幂等）；与人工标注的 Cohen's κ 及其 95% CI 被如实报告 | WP4 归因器 |
| **RQ4** | 在消费级单机（8 GB 内存、Windows 原生、串行）与 100 h 预算下，一条**可复现**的 Agent 评测流水线的最低成本是多少？ | 一条命令跑完一层评测；单位评测成本（token/局、墙钟/局、延迟/决策）可测量；干净环境可复现主表 | WP5 实验与报告 |

四个问题构成一条链：**环境可信（RQ1）→ 指标可测（RQ2）→ 失败可归因（RQ3）→ 结论可复现（RQ4）**。任一环不成立，后面的结论都不成立，这也是本项目把"正确性优先于功能量"列为第一原则的原因。

### 3.2 可判定的规则子集环境

**目标**：一个规则可信、状态可复现、局部最优可精确求解的 Balatro 规则子集引擎。

**范围（覆盖 / 不覆盖必须同时写进报告）**：

| 维度 | 覆盖（v1 规则集） |
|---|---|
| 牌与手牌 | 标准 52 张（4 花色 × 13 点数）；每回合抽 8 张 |
| 出牌 | 选 1–5 张，计分 `chips × mult` |
| 牌型 | 9 种：高牌 / 对子 / 两对 / 三条 / 顺子 / 同花 / 葫芦 / 四条 / 同花顺 |
| 小丑（Joker） | 8 个（`+chips` ×3、`+mult` ×3、`×mult` ×2），按槽位从左到右触发，3 个槽位 |
| 盲注 | 3 档，目标分 300 / 800 / 2000，每档 4 手 + 2 弃 |
| 商店 | 极简 3 选 1 个 joker，**无金钱系统** |
| 终局 | 通过 3 档为胜利；手牌用完未达标为失败 |

**明确不覆盖**：金钱/利息、开包、塔罗与星球消耗牌、Boss 盲注负面效果、牌组改造、稀有度、跳过盲注、卡牌增强/版本、Joker 稀有度与套娃联动。这份"不覆盖清单"是可信度的一部分——**说清边界比假装完整更专业**。

**关键实现约束**：

1. **单一事实来源**：规则只在 `bench/engine.py` 实现一份，MCP Server 只做参数校验与转发，禁止第二份实现（两套规则必然漂移）。
2. **可复现的硬要求**：`rng_state` 必须能完整往返（`getstate`/`setstate`），并随场景版本、模型版本、配置版本一起写入结果文件头；否则"同 seed 复现"是空话。
3. **合法动作枚举**：1–5 张组合上限 `Σ C(8,k) = 218`；等价牌（同花色同点数）去重后通常降到 60–80 个；动作统一编码为 `play:0,2,3` / `discard:1,5` / `choose_joker:1`。
4. **四处高频错误必须专项覆盖**：牌型判定优先级（先同花顺后同花）、A 的点数（顺子中可作 1 或 14，计分按 11）、joker 触发顺序（`+mult` 与 `×mult` 前后影响结果）、取整时机（先算完 chips/mult 再 `floor`）。

**验证方式（对拍）**：不用 Mod 链（安装 Lovely + Steamodded + balatrobot 约 3–5 h 且版本脆弱），改为**人工取样 20 个局面 + 5 例第三方算分器抽检**：分层覆盖无 joker 6 局 / 单 joker 6 局 / 双 joker 5 局 / 含 `×mult` 3 局，逐条比对引擎分数与真实游戏分数；另用交互式算分器复算 5 个基础局面作外部校验。**规则：任何不一致必须追到根因并修正后重测，不允许"大致一致"；第三方抽检的差异要记录而非强行对齐。**

### 3.3 分层评测集与 Oracle 体系

**场景分层（共 60 个）**：

| 层 | 数量 | 构造 | 测的能力 | 决策类型 |
|---|---|---|---|---|
| L1 基础 | 20 | 单回合、无 joker、标准牌型 | 会不会选最优牌型 | play |
| L2 组合 | 20 | 带 1–2 个 joker，涉及 `+chips` 与 `×mult` 的取舍 | 懂不懂机制与优先级 | play |
| L3 长程 | 15 | 3 盲注小局（含弃牌、含商店 3 选 1） | 资源分配、面向未来的规划 | play / discard / choose_joker |
| L4 极限 | 5 | 高目标分、必须搏特定牌型 | 风险决策 | play / discard |

规模定为 60 而非 280：3 组配置 × 60 场景 = 180 episode，已是本机（8 GB、串行）的时间上限。**宁可 60 个可信，不要 280 个跑不完。**

**Oracle 分层，且必须标注精确性**：

| 层 | 定义 | 实现 | 精确性 | 用途 |
|---|---|---|---|---|
| **O1 Local Oracle（play）** | 当前局面所有 `play` 动作中即时分最高者 | 全枚举 218 → 取 max | **exact** | 主指标 regret 的分母 |
| **O2 弃牌 EV（discard）** | 每个 discard 动作执行后，下一手 Local Oracle 分的期望 | 对剩余牌堆做 K=50 次固定种子抽样补牌求均值 | **approx** | 评估弃牌质量，仅作排序参考 |
| **O3 Episode 参照** | 全程贪心（每步选 O1 最优）得到的累计分 | 模拟执行 | **approx**（贪心上界，非全局最优） | 长程参照，不进主指标 |

**严禁宣称**：局部最优 = 全局最优；O3 贪心分 = 该局面理论最高分。为防 oracle 自身有 bug，设置三重校验：`best_score ≥ 任意随机动作得分`、同 seed 重算 `best_score` 完全一致、人工抽 5 个场景复核（含 L4 搏牌型场景）。

### 3.4 指标体系与统计方案

指标不是越多越好，关键是**每个指标都能说清"衡量什么、不衡量什么、是精确还是近似"**：

| 指标 | 定义 | 适用 | 精确性 | 局限（必须写进报告） |
|---|---|---|---|---|
| **Local Regret**（主） | `(best − actual) / best` | L1–L4 的 play 决策 | exact | 只衡量"这一步"，不含未来 |
| **Action Optimality** | 命中最优动作的比例（并列算命中） | L1–L4 | exact | 对"次优但接近"不敏感 |
| **Legality Rate** | 合法工具调用 / 总调用 | 全部 | exact | 只反映协议层 |
| **Discard EV Gap**（辅） | `(EV_best − EV_actual) / EV_best` | L3 的 discard 决策 | **approx** | MC 误差，只作排序参考 |
| **Episode Progress** | 通过的盲注档数 / 3 | L3 | exact | 粒度粗、方差大 |
| **Cost / Latency** | 每局 token、每局墙钟、每决策延迟 | 全部 | exact | 受网络波动影响 |

**边界处理**（否则 regret 会被算错）：`best_score == 0` 的局面不计入 regret 并单独计数；该出牌却选择 discard 时记 `actual = 0`、`regret = 1`；未做任何动作即终止的 episode 记 `premature_stop`，不参与 regret 均值，单列比例。

**统计设计**：配对键固定为 `(scenario_id, seed, model_config_version, prompt_version, tool_version)`，只变模型/Prompt；连续指标用配对 Wilcoxon signed-rank（报 p、rank-biserial 效应量、bootstrap 95% CI），二值指标用 McNemar，3 次两两比较用 Holm 校正；**事前做 power analysis**，样本量不足则主动降低主张（只报描述统计 + CI），不做事后凑显著。

### 3.5 确定性的失败归因器

这是全项目最有价值、也最容易被追问的部分。设计原则：**确定性优先**（能用状态差分/字符串比对判定的，绝不交给 LLM）；**精确与启发式分开标注**；**多标签 + 主次因**；**每个判定必须有可回放的证据链**；**允许"证据不足"**。

| ID | 失败类别 | 精确性 | 一句话定义 | 判定依据 |
|---|---|---|---|---|
| **F1** | `illegal_action` 协议/合法性错误 | exact | 工具参数非法、工具不存在、调用被环境拒绝 | `tool/result.isError` + 工具白名单 |
| **F2** | `miscalculation` 计算错误 | exact | Agent 明确声称的分数与环境真实得分不一致 | 正则抽取声称分 vs `score_delta` |
| **F3** | `rule_hallucination` 规则幻觉 | exact | 引用了不存在的 joker / 牌型 / 规则 | joker 名称表 + 牌型词典（均取自引擎，不另建） |
| **F4** | `planning_shortfall` 规划不足 | **heuristic** | 选择了显著次优动作，且其选择与"只看即时收益"一致 | regret ≥ 阈值且存在后续决策 |
| **F0** | `insufficient_evidence` | — | 未命中任何规则，或证据不足以归类 | 兜底 |

**LLM 只能做解释，不能做判定**：判定结果可由 LLM 事后转写成一段自然语言解释，但解释文字不进任何统计。F4 必须标注为启发式——高 regret 只说明"这步不好"，不能证明"因为短视"，报告中只用于分组统计，不作因果结论。

**验证**：同一条 trace 两次运行输出完全一致（幂等）；每条输出都有 `rule_id` 与 `evidence`（含 `state_hash`，可回链到 `episode.jsonl`）；分层抽 30 条做人工标注并报告 Cohen's κ 与 CI，**不为了达到 κ ≥ 0.7 而调标签**。产出"难度层 × 失败类型"的堆叠分布图，回答"失败构成随难度如何变化""哪一类占比最高"。

| 组 | 模型 | Prompt | 想回答 |

| **A** | 本地 4B（q4） | 直接给动作 | 下界基线 |

### 3.7 技术路线与可行性

```text
dsh（Headless，Windows 原生）
  被测 Agent 只看到 4 个工具：get_state / play_cards / discard_cards / choose_joker
        │  MCP (stdio)   ← 已在 W1 验证可用
bridge/server.py（薄壳，≈80 行）
        │  import（同进程，零 RPC）
bench/  ← 唯一的规则权威
  model.py · score.py · actions.py · engine.py · oracle.py
  scenarios.py · metrics.py · runner.py · trace.py · attrib.py · report.py
        │
runs/<run_id>/episode.jsonl + report.md + figures/
```

**架构决策**：不分服务、不写 DSH 原生插件——MCP Server 与规则引擎同在一个 Python 包内，靠 `import` 连接。规则只能有一份实现，多一个宿主就多一份不一致风险，且 8 GB / 单人项目没有性能收益。

**可行性依据**：W1 已打通 MCP 链路（`bridge/server.py` 的 `balatro_bridge`，stdio 传输，initialize / tools/list / tools/call 全通，trace 完整且 `isError: false`，证据见 `evidence/W1/`）；工具形态精简为 4 个、schema ≤ 900 token，适配 4B 模型有限的上下文；规则子集规模（52 张牌、9 种牌型、8 个 joker、3 档盲注）是单人 20 h/周可完成的工作量；对拍用人工取样而非 Mod 链，把环境成本压到 2 h。

**待验证假设**：W1 的 `get_state` 目前返回硬编码 placeholder，真实状态读取、动作控制、规则引擎与策略评测**均尚未开始**；本项目当前不具备"Agent 会玩 Balatro"的能力，这一点在报告与对外表述中必须保持一致。

### 3.8 实施风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 规则子集与真游戏不一致 | 结论外部效度低 | 20 局面单步分数人工对拍 + 5 例算分器抽检；报告写清覆盖/未覆盖 |
| 4B 模型一局都打不完（提前终止） | 数据稀疏 | 场景以单回合为主（L1/L2 占 2/3），长程只占 1/4 |
| 样本量不足以做显著性 | 结论不可靠 | 事前 power analysis；不足则只报描述统计 + CI |
| 归因器把"启发式"当"确定" | 学术不严谨 | 每类标注 exact/heuristic，heuristic 类不给强结论 |
| 扩功能导致 W2 延期 | 全局崩 | 每周硬性 20 h 上限 + 明确砍单顺序 |
| 真实游戏对拍耗时 | 挤占开发 | 上限 2 h，抽 20 局 + 5 例算分器抽检 |

**砍单顺序（真超时按此执行）**：L4 对抗场景（5 局）→ 极简商店 → 第三组配置（云端 CoT）→ `planning_shortfall` 判定器 → 对拍 25 → 12 局。**单测、对拍、trace 完整性、主表、报告绝不能砍。**

**明确不声称**（写进报告限制章节）：

1. 不声称"局部最优 = 全局最优"——O1 只覆盖当前局面，O3 只是贪心上界。
2. 不声称"复刻了完整 Balatro"——只覆盖 9 种牌型、8 个 joker、3 档盲注、无金钱系统。
3. 不声称"证明了因果关系"——F4 是启发式分组，不是因果识别。
4. 不声称"超越 SOTA"——本项目没有可比的 SOTA，它是评测实践而非新算法。
5. 不声称"首次提出"——失败分类学与 regret 指标在文献中已有先例（详见第 2 章），本项目的贡献在于**在可判定环境里把"精确归因"做成可复现的工程闭环**，并用一致性检验报告其可信度。

### 4.3 学术与工程产出

- **学术侧**：一份可复现的评测协议（环境版本 + 场景版本 + 模型版本 + 工具版本 + 统计方案），可作为"小模型 Agent 诊断"的案例研究；一份失败分类学在卡牌决策域的应用与一致性证据。
- **工程侧**：Windows 原生、8 GB 内存、无 GPU 依赖的完整评测栈；MCP 驱动的 Agent 接入样板；单位评测成本（token/局、秒/局、秒/决策）的度量。
- **方法侧**：把"精确指标"与"近似指标"、"exact 判定"与"heuristic 判定"分列的报告范式——这比多报几个指标更能提升结论的可信度。


## 5 创新点

### 5.1 创新点一：把"可判定性"从口号变成基础设施

**已有工作**：大量论文主张"评测应当可验证"（如代码域的单元测试判分 [34]），但"可验证"在多数环境里只能做到终局正确性检查。**本项目**：把一个完整游戏裁成规则子集，使**每一步的最优动作可枚举、每一手的分数可精确复算、每一个状态可字节级重放**，并把这个能力做成可被 MCP 工具调用的基础设施。

**差异点**：不是"我们也有一个可验证环境"，而是"**我们让'最优'在该环境中成为可计算量**"。这是后续所有指标（regret、optimality、归因）得以成立的前提，也是生态里唯一缺失的一层（见 2.5 节空位一）。

**可检验形式**：25 个单测全绿 + 与真实游戏单步分数 20/20 一致（另 5 例算分器抽检）+ 同 seed 重跑状态与分数完全一致。

### 5.2 创新点二：把过程指标从"估计"变成"测量"

**已有工作**：AgentBoard 的 progress rate [33] 与 BALROG 的细粒度进度 [52] 已经把过程指标做成一等公民，但进度依赖人工/模型标注的子目标分解，是"离终点多远"的估计值。**本项目**：用可枚举的 Local Oracle 定义 `Local Regret = (best − actual) / best`，其中 `best` 由穷举得到、`actual` 由环境记录，两者都是精确值；并明确标注哪些指标是 `exact`、哪些是 `approx`（弃牌 EV 用蒙特卡洛、episode 参照用贪心）。

**差异点**：现有过程指标回答"推进了多少"，本项目回答"**这一步离最优差多少**"。前者依赖基准作者的分解，后者依赖环境的规则——**后者的误差来源少一个数量级**。

**可检验形式**：Random 基线与 Greedy-Oracle 基线分别落在分布两端；三组配置的 regret 分布可区分；同场景重跑 oracle 与分数一致。

### 5.3 创新点三：确定性的失败归因，而不是"再训一个判官"

**已有工作**：Who&When 把失败归因形式化为新任务，但最好的方法步级准确率仅 14.2% [84]；TRAIL 的最强模型仅 11% [85]；MAST 与 AgentDebug 建立了可用的分类学，但判定仍由模型完成 [86][87]。**本项目**：4 类判定器全部由规则与状态差分实现，其中 3 类为 `exact`、1 类显式标注为 `heuristic`；每条判定带 `rule_id`、`state_hash` 与可回放证据；同一条 trace 两次运行输出完全一致（幂等）。

**差异点**：把归因从"生成任务"变成"**查询任务**"——定位不再是模型猜出来的，而是"用同一 seed 与同一动作序列重放到该步，由规则判定该步是否次优"。这是本项目最硬的一块差异（见 2.5 节空位二）。

**可检验形式**：4 类判定器幂等；30 条人工标注 + per-class Cohen's κ 与 95% CI；每条判定可回链到 `episode.jsonl`。

### 5.4 创新点四：让"失败类型"与"指标损失"可换算

**已有工作**：MAST 是系统级分类 [86]、AgentDebug 是模块级分类 [87]、TRAIL 是通用 trace 级分类 [85]，三者的类别都无法直接换算成"分数损失"。**本项目**：4 类失败直接挂在 Local Regret 与 Action Optimality 上——`illegal_action` 对应合法性损失、`miscalculation` 对应声称分与真实分之差、`rule_hallucination` 对应不存在的机制被引用、`planning_shortfall` 对应高 regret 步。于是可以回答"**这一类失败一共损失了多少分**"，而不只是"出现了多少次"。

**差异点**：失败归因从"描述性统计"升级为"可折算的损失归因"，这是成本收益分析（该修哪一类失败）的前提。

### 5.5 创新点五：小样本、低成本、可复现的评测协议

**已有工作**：Agent 评测普遍被批评"只看准确率、不看成本、不可复现" [79]，且"放出代码 ≠ 可复现" [81]。**本项目**：把预注册（主指标、阈值、样本量、剔除规则在跑实验前冻结并打 tag）、`exact/approx` 标注、单位评测成本、一键复现脚本、证据归档写成硬性验收项；在 8 GB 内存、Windows 原生、无 GPU 的条件下跑完 3 组 × 60 场景。

**差异点**：不是"我们样本更大"，而是"**样本不大时也知道结论的边界在哪**"——事前 power analysis、不足则只报描述统计与置信区间、不做事后凑显著。

### 5.6 不声称的东西

1. 不声称"局部最优 = 全局最优"——Local Oracle 只覆盖当前局面，贪心参照只是上界近似。
2. 不声称"复刻了完整 Balatro"——只覆盖 9 种牌型、8 个 joker、3 档盲注、无金钱系统。
3. 不声称"证明了因果关系"——`planning_shortfall` 是启发式分组，不是因果识别。
4. 不声称"超越 SOTA"——本项目没有可比的 SOTA，它是评测实践而非新算法。
5. 不声称"首次提出"——失败分类学与 regret 指标在文献中均有先例 [37][84][86]；本项目的贡献是**在可判定环境里把"精确归因"做成可复现的工程闭环**，并如实报告其一致性。

### 6.4 生态空白与本项目定位（含一处必须处理的风险）

**生态里"能操作真游戏"和"能算分"已经成熟，"能评测但只给总分"已有两个项目，"能精确判定 + 能归因"是空的。**

具体有六块空白：

1. **没有"无需游戏本体"的确定性评测环境**：要么绑真游戏（不可 CI），要么只做局部（算分器/模拟库/种子工具），没有第三条路。
2. **没有失败归因层**：非法动作只被计数（`legality`），不被分类、不被定位到具体步。
3. **没有固定场景集**：现有工具的目标都是"跑完整局"或"搜种子"，没有"60 个单点决策局面 + 每个局面的最优动作"这种东西。
4. **没有 oracle 驱动的过程指标**：没人算 regret、best-action match、oracle 分差。
5. **没有规则实现之间的一致性基准**：各实现覆盖互相矛盾（EFHIII"少数 joker 不准"、balatro-rs 74/150 jokers、Divvy 只覆盖影响分数的 joker），且没有"同一局面、多实现对比"的测试集。
6. **没有统一的 action / state schema**：balatrobot 用手牌下标、balatro-rs 用动作枚举、smods 用对象回调，三者不可互换，导致跨实现结果不可比。

**风险（必须处理）**：`coder/balatrobench` [95] 与本项目**同名**，它做的是 LLM 对局记录的排行榜与结果分析。两者可互补（我们产出结构化失败标签，它擅长展示），但名字相同会让评审第一反应是"这不是已经有了吗"。

**处理建议**（三选一，建议第 2 项）：

1. 保留 `BalatroBench` 作为内部代号，对外一律用副标题限定：**"BalatroBench：可判定失败的 Balatro 子集评测"**；
2. 改用规划中已有的备选名 **`CardBench-Lite`**，在报告中一句话说明与 `coder/balatrobench` 的区别；
3. 直接用描述性名字（如 `Balatro-Decidable-Eval`），牺牲一点记忆度换取零歧义。

无论选哪个，**报告与 README 的第一段都应显式写出"与 coder/balatrobench 同名但不同目标"**，并把两者的分工写清楚：它做"结果展示与横向比较"，本项目做"环境 + 判定 + 归因"。

### 6.5 对原规划的修订建议

本报告不推翻既有决策，但建议做五处修订（均不影响 100 h 预算）：

1. **命名**：按 6.4 节处理同名冲突，优先级最高（影响所有对外材料）。
2. **规则语义对齐**：W2 实现 effect 解析器时，按 `cardarea × 阶段` 分派（借鉴 [102][104]），而不是自创一套顺序模型；否则对拍会系统性偏差。
3. **动作表示**：动作绑定卡牌稳定 id，不用手牌下标（借鉴 [93] 的教训）；同时在 `episode.jsonl` 里保留下标快照，便于与 balatrobot 的 API 语义对照。
4. **归因报告**：W4 的人工标注环节，把"per-class κ + 95% CI + 混淆矩阵 + 弃权率"写成硬性验收项（借鉴 [80][86]），而不只报一个总体 κ。
5. **`plan/00` 的措辞**：D8 行写的是"4 类 + 证据不足，全部确定性判定"，但 `plan/详细版/04-失败归因器.md` 与本报告 3.5 节都把 F4 `planning_shortfall` 标为 heuristic。建议把 `plan/00` 的该句改为"3 类 exact + 1 类 heuristic"，保持三份文档口径一致。

**三条不可越过的边界（v3.0）**：

1. 自建引擎只实现**真规则的一个严格子集**：实现到的规则必须与真游戏逐位一致；没实现的规则必须在场景中排除，不能"用自定义公式近似"。
2. 训练/开发集可以自建，但**每个进入评测集的局面必须有真游戏来源或真游戏回放证据**；只有自建、没有真游戏验证的局面不得进入主表。
3. 真实游戏是**终验**，不是批量主环境：受单局时长、图形依赖、版本链限制，只跑固定的小规模终验；结论按小样本描述统计报告，不做显著性主张。
